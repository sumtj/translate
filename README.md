# SnipTranslate

一个 **60 KB 单文件**的 Windows 划词 / 截图翻译工具。双击即用、托盘常驻、纯热键驱动，
不需要安装程序，不需要任何额外运行时。

## 快速开始

1. 双击 `SnipTranslate.exe`
2. 右下角托盘出现蓝色「译」字图标，就表示已经就绪
3. **左键点击图标不会有任何窗口弹出**（和 Snipaste 一样），只有右键才出菜单
4. 直接用下面的热键

## 热键

只保留两个：

| 热键 | 功能 |
| --- | --- |
| **`Ctrl + D`** | **划词翻译** — 先用鼠标选中文字，按一下即翻译 |
| **`Ctrl + S`** | **截图翻译** — 屏幕变暗后拖拽框选，松手自动识别并翻译 |

其余三个功能**默认不占用任何快捷键**，从托盘右键菜单调用即可：

| 托盘菜单项 | 功能 |
| --- | --- |
| 截图 OCR | 框选屏幕但只识别文字，不翻译 |
| 输入翻译 | 弹出结果窗自己打字（跟 Ctrl+D 没取到词时是同一个） |
| 朗读上次 | 用美式发音读上一次的原文（也可以直接双击结果窗里的文字） |
| **开机自启** | 勾选开关，详见下面 |

### 没选中文字时按 Ctrl+D

会自动弹出**跟划词翻译一模一样的窗口**，只是原文区是空的、可以打字：

```
┌──────────────────────────────┐
│ 📌 🔊                        │  ← 图钉和朗读按钮，跟平时一样
│ ▏                            │  ← 光标在这里，直接打字
│                              │
│ ──────────────────────────── │
│ 输入要翻译的内容，回车翻译…   │
└──────────────────────────────┘
```

- **回车**翻译，**Shift+回车**换行
- 译文出在**同一个窗口**里，不是另开一个
- 出结果后原文**仍然可以改**，改完再回车就是重新翻译
- 窗口跟着鼠标弹、跟着内容长高、Esc / 点外面关闭、图钉、朗读按钮 —— **全都跟划词翻译一样**

> 菜单里的「输入翻译」用的是同一个窗口，只是没有"没取到词"这个前提。
> 托盘菜单里也可以随时调它。

### 取词速度

取词靠的是「模拟 Ctrl+C → 等剪贴板序号变化」，所以**等多久**直接决定手感：

| 情况 | 耗时 |
| --- | --- |
| 有选中文字 | **4 ~ 9 ms**（浏览器 / 记事本 / Electron 都一样） |
| 没选中文字（弹输入窗） | **101 ms** |

这两条路径一开始分别是 63~93ms 和 **1296ms**，按下去像卡住了。做了三件事：

1. **等剪贴板的预算 1000ms → 100ms**。实测真正需要等的只有 4~9ms，100ms 已是十倍余量。
   以前没选中时要白等满一秒才弹输入窗。慢程序取不到词的话，调大配置里的 `ClipboardWaitMs`。
2. **去掉弹起修饰键后的 35ms 死等**。那段等待的假设是"要给目标窗口时间处理 key-up"，
   但 key-up 和后面的 Ctrl+C **走的是同一条输入队列，顺序本来就有保证**。
   实测改成 0ms 后连做 4 次取词全部成功（4~9ms）。真遇到需要间隔的程序，
   可以调 `Native.ModifierSettleMs`。
3. **没取到词就完全不碰剪贴板**。判断"有没有复制成功"靠的是序号变没变，
   跟清不清空无关，所以去掉了没必要的清空+还原（也顺带不干扰你的剪贴板内容）。

> 还有个坑：预算必须用 `Stopwatch` 按**真实时间**算。Windows 默认定时器精度约 15.6ms，
> `Thread.Sleep(10)` 实际会睡 15.6ms —— 按计数自己累加的话，
> "200ms 预算"实际会跑成 312ms。

想给它们也配上快捷键，就在配置文件里填上组合键（例如 `Ctrl+O` / `Ctrl+Alt+R` / `Ctrl+Alt+A`），
保存后托盘右键 →「重新加载配置」。

### 开机自启

托盘右键 →「**开机自启**」，是个勾选开关。

勾选状态**直接读注册表**（`HKCU\Software\Microsoft\Windows\CurrentVersion\Run`），
所以你在「任务管理器 → 启动」里手动把它关掉之后，这里的勾也会跟着消失，不会两边打架。
写的是当前用户的键，**不需要管理员权限**。

也可以用命令行控制（方便脚本化）：

```bat
SnipTranslate.exe --autostart on        :: 开启
SnipTranslate.exe --autostart off       :: 关闭
SnipTranslate.exe --autostart status    :: 只看状态
```

自启时不弹任何窗口，只在托盘出现图标。想让它在启动时冒个气泡提示，把配置里的
`StartupTip` 改成 `true`。

⚠️ **注意**：`Ctrl+D`（浏览器收藏）和 `Ctrl+S`（保存）被本工具全局占用后，在这两个程序里就用不了了。
这是全局热键的固有代价。想避开就改配置文件里的热键。

## 结果窗口

极简：**只有原文和译文**，暗色配色（仿 VS Code Dark+）。

```
┌──────────────────────────────┐
│ 📌 🔊                        │  ← 图钉（钉住不自动关） + 朗读按钮
│ Computing has fundamentally  │
│ changed the way we learn...  │
│ ──────────────────────────── │
│ 计算从根本上改变了我们学习…   │
└──────────────────────────────┘
```

- **窗口高度按内容自动伸缩** —— 内容短窗口就矮，内容长窗口就高，不留白
- **翻译期间显示动态省略号**（`翻译中.` → `翻译中....` 循环），不会白屏
- 窗口**出现的第一帧就是正确尺寸，也在正确位置**，不会先闪一个默认大小/默认位置的大窗再缩回去或跳过来
- 左上角**图钉**：点一下钉住 → 失焦不再自动关闭；再点一下取消（图钉点亮为蓝色）
- 左上角**朗读按钮**是个**开关**：点一下亮起开始读 → 再点变暗立刻停 → 再点从头读
- `Esc` 或**点窗口外面**自动关闭（钉住时不受影响）
- 按住窗口任意位置可以拖动
- **双击**窗口任意位置 = 朗读
- **右键**出菜单：朗读 / 朗读原文 / 朗读译文 / 复制原文 / 复制译文 / 钉住 / 关闭
- 文字可以选中复制（`Ctrl+C`）

### 美式发音

两个引擎，配置项 `TtsEngine` 切换：

| 引擎 | 音质 | 联网 |
| --- | --- | --- |
| **edge**（默认） | Edge 的**神经网络语音**，几乎听不出是合成，自然、有亲和力 | **需要** |
| sapi | Windows 自带的 Zira，拼接式合成，听着比较机械 | 完全离线 |

默认 `TtsEngine = auto`：**先用 Edge 的神经网络语音，合成失败（断网、接口变动）自动退回系统语音**，
保证永远读得出声。

默认语音是 **`en-US-AvaNeural`** —— 官方标注的人设是 Expressive / Caring / Pleasant / Friendly，
是最有亲和力的年轻女声。想换别的改 `TtsVoice` 即可：

| 语音 | 感觉 |
| --- | --- |
| `en-US-AvaNeural` | **默认**，最有亲和力 |
| `en-US-EmmaNeural` | 活泼（Cheerful / Conversational） |
| `en-US-JennyNeural` | 温柔（Friendly / Considerate / Comfort） |
| `en-US-MichelleNeural` | 成熟亲切 |
| `en-US-AriaNeural` | 自信（Positive / Confident） |
| `en-US-AnaNeural` | 童声 |

语速用 `SpeechRate` 调（-10 最慢 ~ 10 最快），两个引擎都吃这个值。

朗读时会自动挑**英文的那一边**：原文是英文就读原文；如果你是中译英（原文中文），就读译文。
学英语要听的是英文，不是中文。

三个触发入口：**朗读按钮** / **双击窗口** / 单击**托盘右键菜单 →「朗读上次」**。

**朗读按钮是个开关**，跟播放器一样：

| 操作 | 效果 |
| --- | --- |
| 第 1 次点 | 按钮**亮起**，开始朗读 |
| 朗读中再点 | 按钮**变暗**，立刻停 |
| 停掉后再点 | **从头**开始读 |
| 读完了自动变暗 | 再点就是从头读 |

**窗口一关（Esc / 点窗口外面 / 托盘退出），声音会同步停掉。**

### 点一下就出声（延迟优化）

Edge 合成本来要等 **1~2 秒**才出声，实测延迟是这么分布的：

| 阶段 | 耗时 |
| --- | --- |
| **连接 + 握手（TCP + TLS + WebSocket）** | **~1200 ms** |
| 发请求 | 2 ms |
| 首包到达 | 550 ~ 1150 ms |

**握手占了总延迟的 65%**，所以做了两件事：

1. **连接复用** —— WebSocket 用完不关，下次直接在同一个连接上发新一轮请求。
   实测：新建连接 `1159ms / 全部 1812ms` → 复用 `0ms / 全部 850ms`，**快了 2 倍多**。
2. **预合成** —— 翻译结果一出来，就在后台把发音合成好放进缓存。
   等你读完再点朗读时，音频早就准备好了。实测**点击到出声 1 ms**。

预合成可以用配置关掉：`PrefetchSpeech = false`（关掉后点朗读会先等 1~2 秒）。

合成要 1~2 秒，这期间朗读按钮会先点亮，不会让你以为点了没反应。
播放途中点停止是**立即生效**的，不会卡住界面。

> **实现说明（踩过的坑）**
>
> Edge 的 TTS 接口有三个门槛，缺一个就是 403 或无声：
> 1. **必须带 Edge 的 User-Agent**。但 .NET 自带的 `ClientWebSocket` **不允许设置 User-Agent**
>    （System.Net 把它列为受限标头，`SetRequestHeader` 直接抛异常）。
>    所以这里自己用 `TcpClient` + `SslStream` 实现了 WebSocket 握手和分帧（见 `RawWebSocket.cs`）。
> 2. 2024 年起必须带 `Sec-MS-GEC` 参数：把「以 1601-01-01 起算、按 5 分钟取整的 100 纳秒数」
>    拼上 TrustedClientToken 做 SHA256。
> 3. 输出格式要用 **MP3**（`audio-24khz-48kbitrate-mono-mp3`）。
>    试过 `riff-...-pcm`，服务端会接受请求、回 `turn.start`，**但一个字节音频都不发**。
>
> 播放方面：WAV 用 .NET 自带的 `SoundPlayer`，MP3 走 `winmm` 的 MCI 接口（`AudioPlayer.cs`），
> 都是系统自带能力，**没有引入任何第三方解码库**。
>
> **MCI 必须跑在 STA 线程上。** 界面里朗读是在线程池（MTA）线程上跑的，直接调 MCI 会报
> `MCIERR_CANNOT_LOAD_DRIVER (266)` —— 驱动加载不起来，表现就是**点了朗读完全没声**。
> 而命令行 `--say` 是 `[STAThread]` 主线程，所以同样的代码在命令行测是好的、到界面上就哑了。
> 修法：`Speech.PlayAudio` 专门开一个 `ApartmentState.STA` 的线程来播（`Speech.cs`）。
>
> 另外**播放失败一定要往外抛**，不能吞掉 —— 吞掉就不会回退到系统语音，用户只会觉得「没声」。
> 现在播放失败会自动退回 SAPI，最差情况是听到 Zira，而不是完全没声音。
>
> **MP3 不能用 `play ... wait`。** 那个子命令会一直阻塞，锁被占着，于是播放途中点「停止」
> 会拿不到锁 —— 界面冻住，声音也停不下来。改成不带 `wait` 的 `play` + 轮询 `status ... mode`，
> 停止就能立刻插进去（实测播放中途停止耗时 0 ms）。
>
> 停止还要能**取消在途的合成**：合成有 1~2 秒，这期间用户可能已经点了停止，
> 合成回来如果不查令牌就会「按了停止又自己响起来」。所以 `Speech` 里有个 `_speakToken`，
> `Stop()` 会自增它，合成结束后先比对令牌再决定放不放。
>
> **MCI 的别名不能跨线程用。** 这是最难查的一个：界面线程调 `stop <别名>` 会报
> `MCIERR_INVALID_DEVICE_NAME (263)`（"指定的设备未打开"），命令失败、声音就一直放下去。
> 但同一个别名在开它的那个播放线程里查询 `status` 却是好的 —— 所以只看代码完全看不出来。
> 修法：**谁开的设备谁负责关**。`Stop()` 只改一个代数标志，由播放线程自己发现并 `stop`/`close`。
> 这个 bug 的连锁反应是：声音停不下来 → MCI 一直占着临时文件 → 下一段朗读写文件失败 →
> 退回系统语音 → **之后一路都是机械音**。所以「点窗口外不停止」和「声音变机械了」是同一个根因。
>
> **每次播放必须用独立的临时文件和别名。** 之前固定用 `tts_audio.mp3`，
> 上一段还在放的时候这个文件被设备占着，下一段直接写不进去。

配色可以在配置里换：`Theme = dark`（默认）/ `light`。

## 必读：热键没反应怎么办

如果你的按键被输入法或某些常驻软件（抖音、微信、音乐播放器之类都爱抢键盘）截走，
本程序内置了**底层键盘钩子（`WH_KEYBOARD_LL`）**兜底 —— 它在输入链路更靠前的位置截获按键，
而且 Windows 的底层钩子是「后装的先被调用」，所以本程序的钩子优先于那些早就在跑的软件。

排查顺序：

1. **看日志**：`%TEMP%\SnipTranslate\app.log`（托盘右键 →「查看日志」）
   - 有 `RegisterHotKey 成功: 划词翻译 = Ctrl+D` → 注册成功
   - 有 `键盘钩子已安装` → 兜底通道也就绪
   - 按键后**没有任何新日志** → 按键根本没进到程序，多半是**以管理员身份运行的窗口**在挡
     （Windows 的 UIPI 机制：普通权限程序收不到发往管理员窗口的按键）
2. 换一组冷门热键，比如 `Ctrl+Shift+F9`，保存后托盘右键 →「重新加载配置」
3. 或者右键快捷方式 → 属性 → 勾选「以管理员身份运行」

## 工作原理

| 环节 | 做法 | 代价 |
| --- | --- | --- |
| 界面 | C# + WinForms，目标 .NET Framework 4.8 | Windows 自带，**无需安装** |
| 截图 | GDI+ `CopyFromScreen`，支持多显示器与负坐标 | 无 |
| 选区 | 无边框全屏窗口盖住冻结画面，拖拽画框 | 无 |
| OCR | `Windows.Media.Ocr`（系统自带引擎），进程内直接调用 | **离线**，20~60 ms |
| 翻译 | 免费接口：Google / 有道 / MyMemory，按顺序自动降级 | 需联网 |
| 词典 | 有道 `jsonapi`，取美式音标与释义 | 需联网 |
| 发音 | `System.Speech` + `Microsoft Zira Desktop (en-US)` | **离线** |
| 热键 | `RegisterHotKey` + `WH_KEYBOARD_LL` 双层 | 无 |

**为什么这么小**：只依赖 Windows 自带的 .NET Framework 4.8 和系统组件，一个第三方库都不打包。

### 几个踩过的坑（代码里都有注释）

- **钩子回调必须立刻返回，而且要装在自己的线程上**。这是最隐蔽的一个 bug：最初把取词动作
  （最长要等 1 秒剪贴板）直接放在钩子回调里同步执行，超过了 Windows 的 `LowLevelHooksTimeout`
  （默认 300 ms）。系统判定钩子超时后**不再采纳它的返回值** —— 于是按下的键继续传到
  `RegisterHotKey`，一次按键触发两次（实测两次相隔约 1 秒），第二次还会在截图框选窗口上面
  再叠一层全屏遮罩。另外钩子装在 UI 线程上时，UI 一忙（截整屏要 200 ms）同样会超时。
  现在：钩子跑在自己的线程 + 自己的消息循环，回调只做匹配，动作用 `BeginInvoke` 丢回 UI 线程。
- **OCR 结果不能简单地把所有行用空格拼成一句**。原先的做法是每行 `Trim()` 后用空格连接，
  结果截图翻译出来的原文永远是一整段，屏幕上的排版全丢了。
  现在改成按行重组，判据是：
  - 上一行以句末标点（`.!?;:。！？；：…`）结尾 → 认为一段结束，**换行**
  - 下一行以小写字母或收尾标点（`,)]}，）】、`）开头 → 认为是同一句的续行，**用空格接上**

  这样"三行各自独立的句子"保持三行，而"一句话被屏幕宽度折成两行"会被正确合成一句。
- **热键动作要加互斥**。截图框选是模态窗口，期间再来一次热键会叠加第二层遮罩。
- **结果窗口必须在 `Show()` 之前就把尺寸算好**。WinForms 的 Form 如果没显式设过
  `ClientSize`，第一次 `Show()` 出来是默认的 300×300 —— 表现就是"按了热键先闪一个大白窗，
  等译文回来才缩成正常大小"，看起来又卡又闪。现在构造函数末尾就调用 `FitToContent()`。
- **首次弹出会卡一下，是 JIT 的锅**。第一次构造结果窗要现场编译一大堆布局/绘制/字体代码。
  现在启动后 800ms 在屏幕外用 `DrawToBitmap()` 先把这条路走一遍（不 `Show()`，所以不会闪窗），
  实测预热耗时 20ms，之后第一次弹窗就没有额外开销了。
- **WinForms 的 TextBox 只把 `\r\n` 当换行渲染，单独的 `\n` 会被当成普通字符**。
  从网页、VS Code 这类地方复制来的文本往往是 LF 结尾，不转换的话整段会挤成一行。
  实测：显式 CRLF 的两行文本正常断行，而 LF-only 的五行文本渲染成了一大段 ——
  但用 `WM_GETTEXT` 读控件内容，那 4 个换行其实一直都在。
  现在 `ResultForm` 在写入前统一走 `NormalizeNewlines()` 把任何换行都规范成 `\r\n`。
- **别用 `System.Windows.Forms.Clipboard` 轮询取词**。它底层是 OLE 剪贴板跨进程调用，
  实测每次 `ContainsText()` 要 200 ms 以上，取一次词要 5 秒；遇到残留的剪贴板属主还会直接卡死界面。
  改用 `OpenClipboard` / `GetClipboardData` / `SetClipboardData` 原生 API，配合
  `GetClipboardSequenceNumber()` 判断剪贴板有没有变，取词降到 **~100 ms**。
- **热键触发时要先弹起修饰键**。用户按 `Ctrl+D` 时 Ctrl 还按着，此时直接发 `Ctrl+C`
  会变成 `Ctrl+Alt+C`，目标程序收不到。所以要先把 Ctrl/Alt/Shift/Win 都弹起再发。
- **INI 要剥离行内注释**。不剥离的话 `Ctrl+D   # 划词翻译` 整个串会被当成热键，全部注册失败。
- **`Scale()` 必须总是返回新位图**。曾经在倍数 ≤1 时返回原图，调用方 `using` 掉之后
  第二次调用就报 GDI+「参数无效」。
- **WinRT 类型的编译期引用**：C# 直接调 `Windows.Media.Ocr` 需要 `.winmd` 元数据，
  由 NuGet 的 `Microsoft.Windows.SDK.Contracts` 提供（仅编译期，不进产物）。

### 实测：热键被别的程序抢走时会怎样

用 Pot 做了对照实验（Pot 也占用 `Ctrl+D/S/O`）：

```
先启动 Pot            → Pot 抢到注册
再启动 SnipTranslate  → RegisterHotKey 失败: 划词翻译 = Ctrl+D（Win32 1409 = 已被占用），靠钩子兜底
                        键盘钩子已就绪（独立线程 + 异步派发），优先由它截获按键
按下 Ctrl+D           → SnipTranslate：热键触发 id=1（来源：键盘钩子）→ 取词 102ms → 翻译成功
                        Pot：日志里完全没有任何反应
```

也就是说**本程序的钩子优先于先启动的程序**，两者可以共存而不会互相触发。

## 已知限制

1. **OCR 用的是系统当前安装的识别引擎**。本机只装了中文引擎（`zh-Hans-CN`），
   读英文基本可用，但偶尔有空格和大小写瑕疵（`fox jumps` 认成 `foxjumps`）。
   把 `OcrScale` 调到 3 能改善一部分。**装上英文 OCR 语言功能后会自动切到英文引擎，效果显著变好**
   （切换逻辑已写好，装完即生效，不用改配置）。
2. **美式发音只有 `Microsoft Zira Desktop` 一个女声**，系统自带的。想要男声需另装 SAPI 语音包。
3. 翻译走免费公开接口，不保证长期稳定，也可能有频率限制。某个源失败后会冷处理 120 秒自动切换。
4. 支持中英互译，方向按内容自动判断。

## 自己重新编译

```powershell
powershell -ExecutionPolicy Bypass -File tools-setup.ps1   # 首次：下载编译工具链（约 110 MB）
powershell -ExecutionPolicy Bypass -File build.ps1         # 编译
```

工具链在 `_tools\`，只在编译时用得到，**删掉不影响 exe 运行**。三个包：
`Microsoft.Net.Compilers.Toolset`、`Microsoft.NETFramework.ReferenceAssemblies.net48`、
`Microsoft.Windows.SDK.Contracts`。

图标由 `make-icon.ps1` 单独生成（内嵌 C#，字节布局精确可控）。设计是
**圆角蓝底 + 白色对话气泡 + 字母 A**，不含任何中文；16px 太小放不下气泡，改用放大的白色 A。

生成的是**多尺寸 ICO**（16/20/24/32/48/64/128/256），Windows 按场景取原生尺寸，不做缩放：

| 尺寸 | 格式 | 用途 |
| --- | --- | --- |
| 16 / 20 / 24 / 32 / 48 | DIB（不压缩位图） | 托盘、任务栏、资源管理器中图标 |
| 64 / 128 / 256 | PNG | 大图标 / 超大图标 / 巨幅图标 |

> 为什么不全用 PNG：**`.NET Framework 4.8` 的 `System.Drawing.Icon` 读不了 PNG 压缩的条目**
> （要 256 会返回 128，`ToBitmap()` 直接抛异常）。所以运行时会用到的 ≤48 必须用传统 DIB。
> 而 128 用 DIB 要 67 KB 太浪费，所以 64 以上交给 PNG —— 那些尺寸只有资源管理器用，它读得了。

> 提示：PowerShell 5.1 读 UTF-8 无 BOM 的脚本会按 GBK 解析，
> 所以 `build.ps1` / `tools-setup.ps1` 存的是**带 BOM** 的 UTF-8，改它们时注意别把 BOM 弄丢。
> `make-icon.ps1` 是**纯 ASCII**（英文注释），不受这个问题影响。

## 磁盘与内存占用

**中间文件都是「用完即删」的**，正常使用不会在磁盘上留东西：

| 文件 | 什么时候产生 | 什么时候删 |
| --- | --- | --- |
| `ocr_*.png` | 每次截图/划词 OCR | 同一次调用结束就删（`finally`） |
| `tts_*.mp3` | 每次朗读 | 播放结束就删 |
| `app.log` | 一直写 | 超过 512 KB 自动重建 |
| `SnipTranslate.ini` | 首次运行 | 配置，本来就该留着 |

启动时还会把 `%TEMP%\SnipTranslate\` 里除日志外的所有东西清一遍，兜底处理
「上次被强杀」或者「删的时候文件还被占着」的情况。

**内存做过 50 轮压力测试**（每轮含 OCR + 建销结果窗 + 翻译 + 发音），结论是稳定的：

| 指标 | 第 5 轮 | 第 50 轮 |
| --- | --- | --- |
| 私有内存 | 51.1 MB | 49.7 MB |
| 总句柄 | 728 | 725 |
| GDI 对象 | 11 | 11 |
| USER 对象 | 17 | 18 |
| 线程 | 25 | 24 |

前几轮会涨一点（JIT、OCR 引擎、WinRT 初始化），之后就平了，不随使用次数单调上涨。

想自己复测：`SnipTranslate.exe --selftest stress 50`（只测某一条路径可以加 `ocr` / `form` / `net` / `speak`）。

> 这套测试确实抓到过一个真泄漏：预合成用的 `ManualResetEventSlim` 在 `Wait()` 时会创建
> 一个内核事件对象，而我一直没 `Dispose()` —— 每次预合成漏一个句柄（结果窗那条路径
> 20 轮涨 65 个句柄、13 个线程）。改成 `Monitor`（走对象同步块，不占内核句柄）后完全归零。
> 顺带修掉了另一个问题：连续翻译时预合成会排队堆积，把线程池逼得不停注入新线程；
> 现在同一时间只允许一个预合成在跑。
